# コードとテストのレビュー手順

テストケースの変更時や一定規模以上のコード変更時に、Claudeモデルをレビュー担当ワーカーとして起動して差分を検査します。実装上の不備や設計不変条件からの逸脱、不適切なテスト修正をコミット前に検出することが目的です。

## 発火条件と実行タイミング

次のいずれかに該当する場合は、このスキルに従ってレビューを実施します。

* テストファイルの追加または修正
* 約50行以上の本番コード変更
* 複数ファイルにまたがる本番コード変更
* 重要境界に関わる本番コード変更

重要境界にはCanonical ABI、値のバイナリ形式、JNIやFFMのブリッジ、asyncスケジューラ、Gradleプラグインのクラスローダー分離、JVM 11互換性が含まれます。実行タイミングはローカルでのビルドおよびテストがすべて成功した直後とします。コミットおよびPRの作成は、このレビューと指摘事項の修正を完了させてから行います。

## ステップ1 ワーカーの起動

`swarm` ツールの `add` アクションを呼び出してレビュー担当ワーカーを起動します。`name` には `code-reviewer`、`model` には `claude-opus-5-5-high`、`workspace` には `inherit` を指定します。

`claude-opus-5-5-high` のクォータが枯渇している場合は、`claude-sonnet-5-5-high` を指定します。実行中にクォータ上限へ達した場合も、同じ代替モデルへ切り替えます。

## ステップ2 レビュー指示と検査観点

`brief` には変更の目的、関連するIssueやADRの番号、`git status` と `git diff` を用いてワークツリーの差分を確認する指示を含めます。あわせて、[CLAUDE.md](../../../CLAUDE.md) と [CONTRIBUTING.md](../../../CONTRIBUTING.md) の不変条件を参照するよう伝えます。ワーカーは読み取り専用で検査のみを行い、ファイルを直接編集せずに指摘事項を `@coordinator` 宛てにボードへ投稿させます。

ワーカーには次の4つの観点で差分を検査させます。

* 不変条件の遵守
* 例外とトラップの境界
* リソースと並行処理の安全性
* テストの妥当性と網羅性

不変条件の遵守では、`runtime-api` と `runtime-chicory` におけるJVM 11およびAndroid API 26互換性の維持を確認させます。さらに、WasmtimeとChicoryの両バックエンド間での値形式や関数解決の整合性、`plan.json` バージョンや `decomposer` 成果物の更新漏れ、Gradleプラグインにおけるクラスローダー分離も点検させます。

例外とトラップの境界では、Canonical ABIの検証が仕様の `trap_if` に沿っているかを確認させます。ゲスト起因の違反がインスタンスをpoisonする `ComponentTrapException` になり、ホスト側の引数誤りがpoisonしない `IllegalArgumentException` または `IllegalStateException` になっているかを検査させます。

リソースと並行処理の安全性では、ホスト定義リソースの `rep` 管理と `HostResourceTable` への束縛、破棄時の通知漏れがないかを確認させます。async機能では `SessionLoop` スレッド制約が守られ、同期パスに不要な変更が入っていないかを点検させます。

テストの妥当性と網羅性では、テストのスキップや無効化、`conformance/skip.txt` への安易な追加、アサーションの緩和が行われていないかを入念に確認させます。実装のバグに合わせて既存テストの期待値を書き換えていないかも検査させ、境界値や異常系のテストケースが十分かを評価させます。

## ステップ3 修正とエスカレーション

`swarm_wait` と `read_board` でワーカーのレビュー報告を受け取ります。指摘された実装上のバグやエッジケースのテスト不足は、メインエージェントが自律的に修正します。修正後はローカルのビルドとテストを再度実行し、すべて通ったことを確認した上で必要に応じて `post_message` で `@code-reviewer` に再確認を依頼します。再確認のやり取りは最大2往復までとします。

既存テストケースの期待値を変更する必要があり、かつその変更が仕様変更や公開APIの挙動変更を伴う場合は、自律的に修正を確定してはなりません。また、設計上のトレードオフ判断が必要な指摘を受けた場合も同様です。該当する論点と変更影響を整理し、ユーザーへエスカレーションして確認を求めます。

## ステップ4 ワーカーの終了

すべての指摘への対応とローカルテストの再確認が完了したら、`swarm` ツールの `kill` アクションで `code-reviewer` を終了します。その後、変更のコミットとPR作成へ進みます。
