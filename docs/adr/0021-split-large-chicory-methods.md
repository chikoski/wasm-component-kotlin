# 0021. Chicory が生成する大きなメソッドをバイトコード単位で分割する

| 項目 | 内容 |
| :--- | :--- |
| ステータス | 承認 |
| 日付 | 2026-11-14 |

## 背景

[ADR-0001](0001-chicory-backend-for-android.md) で採用した Chicory のビルド時コンパイラは、Core WebAssembly モジュールの各関数を 1 つの JVM メソッドとして `FuncGroup` クラスに出力します。関数が JVM のクラスファイル制限である 64 KB を超える場合のみ、その関数をインタプリタ実行へフォールバックします。

一方で、実行基盤の最適化コンパイラには 64 KB より小さいサイズ上限があります。HotSpot JVM は既定の `-XX:+DontCompileHugeMethods` が有効な状態において、JVM バイトコードが 8,000 バイトを超えるメソッドを JIT コンパイルしません。Android の ART も、`dex2oat64` による AOT コンパイルと実行時 JIT の両方において、DEX コード単位で 16,383 を超えるメソッドをコンパイル対象から外し、インタプリタ実行へフォールバックします。

`samples/android-glitch-camera` で使用している `png-glitch-component.wasm` を分割なしでビルドしたところ、コアモジュール 0 から 2 のそれぞれで 5 個のメソッドが ART の上限推定値を超え、31 個のメソッドが HotSpot の 8,000 バイト上限を超えました。最大メソッドの JVM バイトコード長は 43,998 バイトでした。このコンポーネントの `nonMinifiedRelease` ビルドを `emulator-5554` 上の `dex2oat64` で最大最適化コンパイルしたところ、`Core0MachineFuncGroup_0` の 4 つのメソッドがコンパイル対象から外れました。除外された内訳は、`func_1554` の 33,364 コード単位、`func_1423` の 24,514 コード単位、`func_315` の 21,771 コード単位、`func_344` の 16,638 コード単位でした。

## 検討した選択肢

この問題に対して 5 つの選択肢を検討しました。

* 実行時フラグや難読化設定のみに頼る案
* Binaryen や Wasm AST の段階で関数を分割する案
* Chicory 本体のコンパイラ生成ロジックをフォークや改修で変更する案
* ディスパッチメソッドの二段分割を含めて独自コード生成へ置き換える案
* Chicory 出力後の JVM バイトコードを ASM で分割する案

実行時フラグや設定のみに頼る案は、既存ビルドパイプラインを変更せずに済む点が長所です。しかし、デスクトップ JVM の `-XX:-DontCompileHugeMethods` に相当するフラグは Android ART には存在しません。また、R8 による縮小は単一メソッド内部の命令数を ART の 16,383 コード単位以下まで減らす保証にはなりません。Android 実環境でのインタプリタ実行を防げない点が短所です。

Binaryen や Wasm AST の段階で関数を分割する案は、Chicory 以外のコンパイラでも再利用できる点が長所です。しかし、Wasm のローカル変数や分岐構造を関数境界を跨いで再設計する必要があり、Binaryen 等の外部ツール依存も増えます。コンポーネント分解時に扱う Wasm 関数数やテーブル構造も肥大化しやすい点が短所です。

Chicory 本体のコンパイラ生成ロジックを改修する案は、64 KB を超えてインタプリタに落ちる関数や `call_dispatch_0` のようなテーブル分岐メソッドを二段分割できる点が長所です。長期的には上流プロジェクトへの貢献が望ましい選択肢です。ただし、即時の独自フォークは上流 Chicory 1.7.5 の更新追従の負担が大きくなります。

独自コード生成へ全面的に置き換える案は、完全な制御を得られる反面、実装と検証の維持コストが現実的ではありません。Chicory が担う Wasm 命令列の意味検証や最適化を再実装する負担が大きすぎるため見送りました。

Chicory 出力後の JVM バイトコードを ASM で分割する案は、上流の Chicory 1.7.5 を無改変のまま使いつつ HotSpot と ART の双方の上限を回避できる点が長所です。一方で、Chicory が生成するメソッドの命令パターンに依存する点が短所です。また、Chicory 自身が 64 KB 上限でインタプリタへ落とした関数はバイトコードが存在しないため分割できません。以上を比較し、即時性と保守性のバランスから ASM による後処理分割を採用しました。

## 決定

`CoreModuleCompiler` のコンパイル後処理として、ASM 9.9.1 を用いた `JvmMethodSplitter` を導入します。目標メソッドサイズは 7,500 バイトとし、あわせて残存する上限超過をビルド時に警告する仕組みを加えます。

`JvmMethodSplitter` は `func_` に数字が続く名前を持つメソッドだけを対象に分割します。各メソッドを走査し、境界の前後でオペランドスタックの深さが 0 となり、領域内部からの分岐先が領域内または領域直後に閉じる連続領域を探します。抽出候補の中からバイト数削減効果を表す `netSavingsBytes` が最大になる領域を貪欲に選び、目標サイズ以下になるまで最大 128 個の `private static synthetic` な補助メソッドである `func_X$s0` 等を切り出します。先頭に配置した保守的なしきい値で収まらない場合は、最小領域サイズを 320 バイトから 180 バイトへ、外部分岐先数の上限を 12 から 20 へ緩めた第 2 段階を続けて実行します。

補助メソッドへの引数には、領域内で参照されるすべてのライブイン変数を渡します。ここには `Instance` や `Memory` などの参照型ローカル変数も含まれます。領域内で更新されて後続コードで参照されるライブアウト変数はプリミティブ型と `boolean` 系整数のローカル変数に限定し、元メソッドのプロローグ直後に 1 回だけ確保する `long[]` 配列へ書き戻します。整数は `I2L`、単精度浮動小数点は `Float.floatToRawIntBits` と `I2L`、倍精度浮動小数点は `Double.doubleToRawLongBits` を用いてビット列のまま `long[]` に格納します。補助メソッドの戻り値は、外部への分岐先がない場合は `void`、外部分岐先がある場合は分岐先識別子を表す `int` とし、呼び出し元がスイッチ命令で分岐先へ振り分けます。切り出し領域の探索時に `long[]` スロットの操作や既存の補助メソッド呼び出しに出会った箇所で探索を打ち切ることで、反復分割時に呼び出し境界を重複して包む現象を防ぎます。

既存不変条件との整合性も維持します。Gradle プラグインは [ADR-0004](0004-isolated-tooling-classloader.md) に基づき `wasm2ktTooling` を独立クラスローダーで実行するため、Chicory が推移的に依存する ASM とツール側の ASM 9.9.1 が Android Gradle Plugin と衝突することはありません。分割処理は既存のクラスファイルバージョンを変更しないため、`runtime-api` や `runtime-chicory` の JVM 11 および Android API 26 互換性に影響しません。また、[ADR-0007](0007-canonical-abi-validation.md) で定めた Canonical ABI のトラップ例外は補助メソッド境界を越えてそのまま送出されるため、トラップ判定やポイズン挙動は変わりません。なお、静的レイアウト情報のみを返す `CoreModuleCompiler.layout` では実バイトコードが存在しないため、分割数や超過数の統計値は 0 になります。

安全性のため、未知の命令構造を含む場合や検証に失敗した場合は元のクラスバイト列へ無加工で戻します。具体的には、例外ハンドラ表である `tryCatchBlocks` が空でないメソッド、メソッド本体に `ASTORE` などの未対応命令を含むメソッド、型推論または ASM のデータフロー解析が成立しないメソッド、`CheckClassAdapter.verify` がエラーを返したクラスは分割をスキップまたは取り消します。なお、`CheckClassAdapter.verify` とフレーム計算を行う `ClassWriter` には `classesDir` を参照する専用 `URLClassLoader` を渡し、`FuncGroup` クラスから兄弟クラスの `CoreNMachine` を解決できるようにしています。また、分割時は既存の `FrameNode` と `LineNumberNode` を削除してフレームを再計算します。

サイズ監視として、分割後の全クラスファイルから `Code` 属性の実バイト長を直接読み取ります。JVM バイトコードが 8,000 バイトを超えるメソッドは HotSpot 上限超過、21,000 バイト以上のメソッドは ART の 16,383 DEX コード単位を超えるおそれがあるメソッドとして集計します。21,000 バイトの基準は、`png_glitch` の通常 `func_*` メソッドで観測した 20,245 JVM バイトあたり 13,569 コード単位、24,557 JVM バイトあたり 16,847 コード単位という約 0.67 から 0.69 の換算比を根拠に保守的な余裕を見て定めた経験的しきい値です。集計値と最大メソッドサイズ `maxMethodCodeBytes` は `CoreModuleCompiler.Compiled` に保持し、`Wasm2KtTasks` と `Wasm2KtPlugin` が配線する `wasm2ktCompileWarnings<Name>` タスクを通じて出力します。

## 結果

この決定により、大きな `func_*` メソッドを含むコンポーネントでも HotSpot JVM と Android ART の双方でコンパイル対象に入る範囲が広がります。`samples/android-glitch-camera` の `png-glitch-component.wasm` では、コアモジュール 0 の 34 個のメソッドが分割され、`func_*` メソッドの DEX サイズは最大 6,724 コード単位まで縮小しました。R8 を有効にした `app-release.apk` でも、生成された補助メソッドは R8 による全面的な再インライン化を受けずに維持され、APK 全体の最大メソッドは 12,056 コード単位に収まりました。`app-nonMinifiedRelease` と `app-release` の双方を `emulator-5554` で `cmd package compile -m everything -f` でコンパイルした結果、`dex2oat64` の命令数上限超過ログは 4 件から 0 件になりました。一方で、`call_dispatch_0` は名前フィルタにより分割対象外であり、15,377 JVM バイト、13,440 DEX コード単位のまま残ります。そのため `png-glitch-component.wasm` や `heavy.wasm` では HotSpot 8,000 バイト上限のビルド警告が 1 件出力されます。`heavy` フィクスチャでは 13 個のメソッドが分割され、最大メソッドが 8,121 バイト、ART 上限超過が 0 件になりましたが、56 KB の wasm 関数である `func_366` だけは Chicory 側で 64 KB 上限を超えるためインタプリタ関数のまま 1 件残ります。

`samples/android-glitch-camera` の `cyber_sort` プリセットを用い、1 フレームの処理時間を分割前後で比較しました。条件は解像度 960×540、`PngFilterOption.NONE`、ウォームアップ 10 回、本計測 20 回です。Host JVM は macOS Apple Silicon 上の OpenJDK 21 で実行しました。Android ART は `emulator-5554` 上の `Medium_Phone_API_36.1` 環境、Android 16、ARM64 ABI で実行し、`debuggable` を無効にした `app-nonMinifiedRelease.apk` を用いました。`debuggable` が有効なビルドは `cmd package compile -m everything` を実行しても `dexopt` が `verify` 状態のままになり、約 1,148.60 ms から 1,173.16 ms の実行時間になるため除外しています。

デスクトップ Host JVM では既定設定のままで 198.27 ms から 10.50 ms に短縮しました。`-XX:-DontCompileHugeMethods` を付けた場合も分割後の 10.99 ms が分割前の 19.71 ms より速く、これは 44 KB 規模の単一メソッドより 7,500 バイト以下に抑えたメソッド群の方が C2 コンパイラの最適化やレジスタ割り当ての負荷が低いためと考えられます。Android ART でも、エミュレーター上の仮想環境という制約を含みつつ、4 メソッドのインタプリタフォールバックが解消したことで 558.92 ms から 334.01 ms へ短縮しました。なお、この計測は単一コンポーネント 1 プリセットでの結果であり、実機 CPU では絶対値が異なります。

本決定に伴う制約と今後必要になる点として、4 つの項目が残ります。

* 21,000 JVM バイト閾値と DEX 換算比のずれ
* ディスパッチメソッドの未分割と 64 KB 超の未救済
* 無言フォールバックの可視化不足
* 分割に伴うスタック深さと行番号情報の変化

第 1 に、`call_dispatch_0` では 15,377 JVM バイトに対して 13,440 DEX コード単位と約 0.87 の換算比が観測されました。テーブル分岐を多く含むメソッドは 18,800 JVM バイト前後で ART の 16,383 コード単位を超えるおそれがあるため、21,000 バイト閾値では警告が出ずに ART がスキップする余地があります。また、警告文中の `max N bytes` は対象メソッド固有ではなくモジュール全体の最大サイズを表示します。

第 2 に、`call_dispatch_0` は名前フィルタにより分割されず、Chicory が 64 KB 上限でインタプリタへ落とした関数も対象外です。大規模モジュールでこれらが性能上のボトルネックになる場合は、上流 Chicory での二段 `tableswitch` 化や関数分割の導入を今後検討する必要があります。

第 3 に、検証エラーや未対応命令で元バイト列へフォールバックした場合も現状はビルド警告を出さず、サイズ計測後の超過警告のみに頼っています。分割を取り消したメソッド数を警告で可視化する改善が今後の課題として残ります。

第 4 に、分割したメソッドでは呼び出しフレームが 1 段深くなるため、深い再帰を行う Wasm 関数では `StackOverflowError` に達する深さがわずかに早まります。加えて、`LineNumberNode` を取り除いて再構築するため、分割対象メソッド内で発生した JVM 例外のスタックトレースではソース行番号が失われます。また、`long[]` フレーム配列は呼び出し先ごとではなく元メソッドの先頭で 1 回だけ確保するものの、関数単位の呼び出しが多いワークロードでは配列確保のコストが加わります。
